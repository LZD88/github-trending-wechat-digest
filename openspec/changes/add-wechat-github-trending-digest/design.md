# Design

## Context

当前仓库是已初始化 OpenSpec 的绿色项目，尚无业务代码；`work/` 中只有前期 GitHub Trending 开源方案调研脚本。实现需要同时处理不稳定的网页数据源、GitHub API 限流、可选中文摘要服务、Server酱消息限制、定时任务延迟和秘密凭据。需求口径见两份能力规格；动机见 `proposal.md`。

日报采用前一晚归档的 GitHub `daily` Trending 滚动榜快照，消息展示实际抓取时间和滚动榜口径。

## Goals / Non-Goals

**Goals:**

- 形成可在 GitHub Actions 免费或低成本运行的单进程应用，默认北京时间每天 08:00 执行。
- 将抓取、规范化、摘要、渲染、持久化和推送解耦，便于单元测试和替换外部服务。
- 默认支持 Server酱，保证凭据不落盘、发送幂等、失败可重试且能够手动预览/补发。
- 保存不含敏感信息的日榜快照和发送记录，让每次运行可追溯。

**Non-Goals:**

- 不登录或自动操作微信客户端，不使用 Web 微信、Hook 或任何非官方个人微信协议。
- 不计算 GitHub 全站所有仓库在严格自然日内的 Star 增量排名。
- 首版不提供多用户、图形化后台、数据库服务或多渠道同时群发。
- 首版不实现 PushPlus 适配器，只保证适配器契约能支持后续新增。

## Decisions

### 1. 采用 Python 命令行应用与 GitHub Actions 调度

Python CLI 提供 `capture`、`run`、`preview`、`test-binding` 和 `resend --date`。GitHub Actions 以北京时间设置 23:55、08:00 和每小时一次检查，按实际启动时间选择采集或发送。采集延迟到次日 02:55 前仍归原榜期。定时发送使用 `run --recover-missing`，在本地归档缺失时读取同日的第三方归档，标明来源和归档时间后发送。

选择原因：Python 对 HTML 解析、HTTP、测试夹具和中文文本处理支持成熟；GitHub Actions 无需常驻服务器且 Secrets 管理与本项目场景匹配。定时任务可能延迟，因此业务日期从计划日期/显式输入计算，执行记录另存实际时间。

备选方案是 Cloudflare Workers Cron，准点性和常驻能力更好，但 HTML 解析、文件归档和本地测试复杂度更高；在出现明显调度可靠性问题前不采用。

### 2. 使用主源直抓与带时间戳备用源

主源请求 `https://github.com/trending?since=daily`，解析页面原始顺序和日榜新增 Star。随后通过 GitHub Repository API 补全仓库简介、语言和总 Star；配置 `GITHUB_TOKEN` 时使用认证请求，未配置时使用匿名额度。

主源失败时调用一个实现相同规范化接口的备用源，首选 `isboyjc/github-trending-api` 的 daily/all JSON，并校验其 `pubDate` 是否在允许的新鲜度窗口内。备用源过期、格式异常或不足以验证榜期时停止正式推送，不发送旧榜。

备选方案是完全依赖第三方 API，接入简单但会把可用性和数据口径交给单一维护者；完全自己维护 Star 事件数据则超出“Trending 热榜”范围且成本显著更高。

### 3. 以规范化领域模型贯穿流水线

内部模型分为：

- `TrendingEntry`：排名、仓库全名、URL、原简介、中文简介、语言、总 Star、日榜新增 Star；
- `DigestSnapshot`：目标榜期、抓取时间、数据源、口径、条目集合和内容摘要值；
- `DeliveryAttempt`：归档保存提供方、脱敏接收配置标识、榜期、尝试次数、最终状态和错误分类。服务方消息标识和原始错误文本不写入归档。

内容摘要值对排序稳定的规范化 JSON 计算 SHA-256。接收配置标识由提供方名称和密钥的不可逆摘要前缀构成，只用于区分配置，不保存 SendKey。

### 4. 中文摘要使用可选的 OpenAI 兼容接口

摘要层接受批量仓库简介，优先保留已有中文；英文简介通过可配置的 OpenAI 兼容端点生成一句中文说明，配置项包括 API Base、API Key 和模型名。提示词限制为忠实翻译/概括，不推测仓库未声明的能力，并对输入输出做长度限制。

未配置摘要服务、超时或返回不合格文本时回退到原始简介；该降级会写入快照状态但不会阻塞日报。该选择避免绑定单一付费厂商，同时允许用户使用兼容服务。备选的公共翻译接口无需密钥但稳定性和隐私边界不可控，因此不作为默认路径。

### 5. 快照与发送状态使用仓库内 JSON 持久化

生成结果写入 `data/digests/YYYY-MM-DD.json`，发送尝试写入 `data/deliveries/YYYY-MM-DD.json`。GitHub Actions 成功或失败后仅提交发生变化且不含秘密的文件；预览模式默认不提交。JSON 使用稳定字段顺序，既可审阅也便于后续迁移。

去重依据为 `provider + recipient_fingerprint + target_date`。成功记录存在时普通 `run` 跳过；`resend` 创建带 `manual_resend` 原因的新 attempt，不篡改原记录。

备选的 Actions Cache/Artifact 不保证长期留存和跨运行可查询；外部数据库对单用户项目过重。

### 6. Server酱适配器负责限制感知、分段和错误分类

推送层定义统一 `DeliveryProvider` 契约，输入标题和一个或多个完整消息段，输出标准化结果。Server酱适配器从 `SERVERCHAN_SENDKEY` 读取凭据，按其 API 限制校验标题和正文，并只在完整项目边界分段。

网络超时、连接错误、HTTP 429 和 5xx 归类为可重试，使用带抖动的指数退避且最多三次；认证失败和请求校验错误归类为永久失败。日志过滤器统一遮盖 SendKey、Authorization 和摘要 API Key。

### 7. 失败策略以“不误发旧数据”为优先

采集任务抓取、校验并生成中文摘要，然后保存快照。发送任务读取归档，再渲染、检查是否已发送并推送。未取得有效榜单时，采集任务报错。缺少目标榜期归档时，发送任务报错。单个可选字段或摘要失败时可降级。

工作流自身以非零退出码暴露失败，并保留脱敏日志及可提交的失败状态。由于唯一通知渠道可能正是 Server酱，首版不尝试用同一失败渠道发送错误告警；用户可从 GitHub Actions 失败通知看到异常并手动补发。

## Risks / Trade-offs

- [GitHub 页面结构变化导致解析失败] → 使用固定 HTML 夹具测试、显式选择器校验、备用源和“旧数据不发送”策略。
- [GitHub Actions 定时任务延迟] → 区分计划榜期与实际执行时间，消息披露抓取时间，并保留手动补发入口。
- [第三方备用源数据过期或停止维护] → 强制校验 `pubDate` 和最小字段集，失败时终止发送而不是静默使用旧数据。
- [Server酱配额或内容限制变化] → 将限制集中在适配器，按项目边界分段，并将 429 归为可重试错误。
- [每日提交使仓库历史增长] → 仅保存精简 JSON；后续可按月压缩或迁移到专用 data 分支，不影响领域模型。
- [摘要模型产生不准确中文] → 提示词限制、长度/空值校验、保留原简介字段并允许降级显示原文。
- [仓库公开时运行记录暴露用户偏好] → 快照只包含公开仓库信息，接收配置仅保存不可逆指纹；如仍敏感，部署说明建议使用私有仓库。

## Migration Plan

1. 创建应用骨架、测试和不含真实秘密的示例配置。
2. 先在本地/Actions 以 `preview` 模式验证抓取、字段、中文摘要和消息分段。
3. 用户在 Server酱完成微信绑定，将 SendKey 添加为 GitHub Actions Secret。
4. 手动运行 `test-binding`，确认个人微信收到测试消息。
5. 手动执行一次正式 `run`，验证快照、幂等和发送记录。
6. 启用每日定时工作流；观察至少一次自动执行后完成上线。

回滚时禁用或删除定时工作流，并在 Server酱后台吊销 SendKey。历史 JSON 不包含密钥，可保留审计或直接从仓库历史之外另行清理；回滚不需要操作微信客户端。
