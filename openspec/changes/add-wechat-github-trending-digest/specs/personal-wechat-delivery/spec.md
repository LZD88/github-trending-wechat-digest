# Spec Delta

## Purpose

该能力用于通过用户主动绑定的合规推送服务把 GitHub 热榜送达个人微信，同时保证凭据安全、消息可读、失败可恢复且不会重复骚扰用户。

## ADDED Requirements

### Requirement: 通过推送服务绑定个人微信
系统 SHALL 通过推送服务的访问密钥向用户已绑定的个人微信发送消息，首个支持的服务为 Server酱。系统 MUST NOT 登录个人微信、索取微信账号密码或保存微信客户端会话。

#### Scenario: 有效 Server酱密钥
- **WHEN** 操作者配置了已绑定微信的有效 Server酱 SendKey
- **THEN** 系统可通过 Server酱 API 向对应微信接收方发送测试消息和日报

#### Scenario: 缺少推送密钥
- **WHEN** 正式发送开始前未配置推送服务密钥
- **THEN** 系统拒绝调用推送接口，并输出不包含敏感信息的配置错误

### Requirement: 安全管理推送凭据
推送密钥 MUST 仅从运行环境的秘密配置中读取，不得写入源码、榜单快照、构建产物或普通日志。所有错误信息和诊断输出 SHALL 对可能出现的完整密钥进行脱敏。

#### Scenario: 运行日志记录请求失败
- **WHEN** 推送接口返回错误且错误上下文包含请求地址或密钥片段
- **THEN** 系统在持久化日志前隐藏完整密钥，仅保留可用于定位问题的非敏感信息

#### Scenario: 生成榜单归档
- **WHEN** 系统保存日报内容和发送状态
- **THEN** 归档中不包含 SendKey、微信标识或第三方服务认证信息

### Requirement: 提供绑定测试
系统 SHALL 提供不会发送正式榜单的测试操作，向绑定微信发送一条带时间戳和环境标识的确认消息，并明确返回测试成功或失败。

#### Scenario: 测试发送成功
- **WHEN** 操作者触发绑定测试且推送服务接受请求
- **THEN** 微信收到一条明确标记为“绑定测试”的消息，系统记录成功时间和服务方消息标识

#### Scenario: 测试发送失败
- **WHEN** 推送服务拒绝测试请求或请求超时
- **THEN** 系统返回可操作的失败原因且不把绑定状态标记为已验证

### Requirement: 生成适合微信阅读的消息
系统 SHALL 使用支持的富文本格式呈现标题、榜期、数据口径、前十项目和项目链接。消息内容超过服务限制时 MUST 按完整项目边界分段，并在每段标注序号，避免截断项目内容或链接。

#### Scenario: 单条消息可容纳完整日报
- **WHEN** 渲染后的日报未超过推送服务的标题和正文限制
- **THEN** 系统使用一条消息发送完整日报

#### Scenario: 日报超过单条限制
- **WHEN** 渲染后的日报超过推送服务允许的正文长度
- **THEN** 系统按项目边界拆分为多条有序消息，并在每条标明当前段和总段数

### Requirement: 避免重复正式推送
系统 MUST 使用“推送渠道 + 接收配置标识 + 目标榜期 + 内容摘要值”作为幂等依据。已成功发送的相同内容不得因调度重试再次正式发送；明确发起的补发操作 SHALL 作为新的发送尝试记录并带补发标记。

#### Scenario: 调度任务重复执行
- **WHEN** 相同榜期和内容已成功推送后，调度平台再次执行同一任务
- **THEN** 系统跳过推送并将结果记录为幂等命中

#### Scenario: 用户明确补发
- **WHEN** 操作者对已发送榜期明确发起补发
- **THEN** 系统再次发送带“补发”标记的日报，并保留与原发送记录的关联

### Requirement: 对暂时性错误进行有限重试
系统 SHALL 对超时、连接失败和服务端限流或 5xx 错误进行有限次数的退避重试；对无效密钥、请求格式错误等永久性失败不得盲目重试。所有尝试结束后 MUST 保存最终状态和可诊断原因。

#### Scenario: 服务暂时不可用后恢复
- **WHEN** 首次发送遇到可重试错误且后续尝试成功
- **THEN** 系统将日报标记为发送成功，并记录发生过重试及尝试次数

#### Scenario: 密钥无效
- **WHEN** 推送服务明确返回认证失败
- **THEN** 系统立即停止自动重试，将发送标记为永久失败并提示更新密钥

#### Scenario: 重试耗尽
- **WHEN** 所有允许的重试均失败
- **THEN** 系统将发送标记为失败，保留下一次可手动补发所需的非敏感上下文

### Requirement: 支持可替换的推送提供方
系统 SHALL 以统一的发送结果和错误分类契约调用推送提供方。新增 PushPlus 等提供方时，不得改变榜单生成、幂等键语义或执行状态格式。

#### Scenario: 使用默认提供方
- **WHEN** 未显式选择推送提供方且配置了 Server酱凭据
- **THEN** 系统使用 Server酱适配器发送消息

#### Scenario: 配置未知提供方
- **WHEN** 配置指定了系统不支持的推送提供方
- **THEN** 系统在发送前拒绝运行并列出可用提供方，不回退到其他渠道
